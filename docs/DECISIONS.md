## M1. Base app, database, demo roles (2026-10-25)

**In plain words.** In M1 I made the engine the only part of the system that touches the database, so permissions,
idempotency and audit logging each live in one place. The engine connects as a limited database role: it can add rows
to the audit log but cannot change them, disable the trigger that guards them, or change the schema, and tests prove
each of those refusals. Permissions are one default-deny function whose expected answers I wrote by hand before the
code, and every order query is also filtered by customer in SQL. Every write needs an idempotency key scoped to the
user and the endpoint; the key is claimed in the same transaction as the write, so two identical requests sent at the
same moment produce one order and one audit row. Demo login uses a signed, expiring token in an httpOnly cookie, and
it is off unless a setting turns it on.

| # | Decision | Why | Alternative considered |
|---|---|---|---|
| D17 | The engine owns all database access; the web app only calls the engine over HTTP. | One place enforces permissions, idempotency and audit (hard rules 4 and 6), and one definition of the tables. | Next.js doing CRUD through its own ORM (faster screens, two data layers). |
| D18 | Plain SQL migrations in `db/migrations/`, applied by a ~100-line runner that stores a checksum per file and refuses an edited one. | Triggers and grants are SQL anyway; the files read top to bottom. | Alembic; yoyo-migrations. |
| D19 | psycopg 3 with hand-written parameterised SQL, no ORM. Rows map to pydantic models with `class_row`. | Every query is visible (hard rule 5); fewer concepts. | SQLAlchemy. |
| D20 | Two database roles. The owner (`POSTGRES_USER`) runs migrations and the seed. The engine connects as `brimline_app`, which has explicit per-table grants only, no `DELETE` on orders, and `SELECT`/`INSERT` only on `audit_log`. The runner refuses a `DATABASE_URL` that is not `brimline_app`. | Defence in depth for the append-only log: the trigger stops mistakes; missing privileges stop a compromised app from changing rows, disabling the trigger, or changing the schema. **Corrected after review (DEFECT_LOG #6, #9):** the first version still let the app forge `id`/`at` and shadow the table with a temp table; 0004 closes both. In this local setup the owner is the container's superuser; a deployment should use a non-superuser owner (M11). | Trigger only. |
| D21 | Session token: `v1.<payload>.<HMAC-SHA256>`, stdlib only, with expiry and `hmac.compare_digest`. Stored in an httpOnly, SameSite=Lax cookie (Secure in production). Demo routes exist only when `DEMO_LOGIN=true`; the default is off. The `.env.example` placeholder secret is refused. | Small enough to explain line by line. Off-by-default means a deployment cannot ship demo login by accident. | PyJWT or itsdangerous; a full auth library (more than a demo login needs). |
| D22 | Idempotency keys are scoped to (user, endpoint, key). The request inserts its key row first, inside the write's transaction, with `ON CONFLICT DO NOTHING`. A concurrent duplicate blocks on the primary key until the first commits, then replays the stored response. A failed write rolls back its claim, so the key can be retried. Same key with a different body is 409. | Exactly-once with no extra locking code; the database does the waiting. | Advisory locks; deduplicating on content. |
| D23 | Permissions are a pure, default-deny `can(actor, action, target)` plus `order_scope()`. The domain layer (`orders.py`) calls them itself, and order queries are also scoped in SQL. Another customer's order is a 404 with the same body as a missing one; unknown customer codes are 403 for customers and 422 only for roles that may list customers. | Routes cannot forget a check; nothing reveals that someone else's order exists. | Row-level security in Postgres (kept as an idea). |
| D24 | Tables are named `machines` (not `printers`), because the shop also has a CNC mill. Orders have one job per line; tasks are a table only, generated by the scheduler in M3. Price rules live in `config/shop.toml` now and become the dated `price_rules` table in M2. | Keeps M1 to its acceptance criteria. | Creating the price tables now. |
| D25 | Seed config is TOML (stdlib `tomllib`), validated by pydantic including cross-references, with a fixed `seed_time` so two seeds are identical. The seed writes no audit rows (it is setup, not an app write). | No extra dependency; a typo fails before any SQL runs. | YAML; Faker. |
| D26 | Web types are generated from the engine's OpenAPI schema (`openapi-typescript`), used with `openapi-fetch`; the gate fails if the committed file is stale. zod validates form input in the web for friendly messages; the engine re-validates and is the authority. | Web and engine cannot drift silently. | Hand-written types. |
| D27 | Next 16 Cache Components stays on. Every session read sits inside `<Suspense>`, request-time fetches call `connection()` first, and nothing session-derived is cached. | Follows the bundled "authentication with Cache Components" guide; no caching means permissions shown are always current. | Turning Cache Components off. |
| D28 | Test isolation: engine tests rebuild `brimline_test`, browser tests reset `brimline_e2e` and run the engine on port 8100 and web on 3100. The engine's clock is a dependency (`utc_now`), fixed in API tests. | Dev data is never touched; date rules are deterministic. | One shared database. |
| D29 | Added dependencies: psycopg, psycopg-pool, pydantic-settings, tzdata (Windows has no system time-zone data); zod, openapi-fetch, openapi-typescript (dev), server-only. | Each is small and has one job; `server-only` makes the build fail if token-handling code reaches the browser. | Doing without (more hand-written code). |
| D30 | ruff `E501` off (the formatter owns line length; long lines left are SQL strings), and `ANN401` off in tests only. | Readable SQL; test clients are untyped. | Splitting SQL into fragments. |
| D31 | An idempotent replay re-reads the order with the user's current permissions and returns that, not the stored snapshot. | A replay is a read and must pass today's checks (hard rule 4, DEFECT_LOG #8). The stored body is still kept for the conflict check and debugging. | Re-checking `order.create` only; deleting keys on permission change. |
| D32 | String inputs use `SafeText` (no NUL), order numbers must match `^BL-[0-9]{4,10}$`, and idempotency keys `^[A-Za-z0-9._:-]{8,200}$`. | Bad input becomes a 4xx at the boundary instead of a database error (DEFECT_LOG #7). | Catching database errors globally (hides real bugs). |
| D33 | Session tokens are `v2` and carry the user's `session_version`; `POST /auth/logout` bumps it in an audited transaction and signs the user out everywhere. Logout needs no idempotency key: after the first call the token is invalid, so a retry is a 401 that changes nothing. | Sign-out must revoke, not just forget (DEFECT_LOG #10). | A per-token denylist (more state to expire). |
| D34 | Known limits kept after review: the app role can still call `pg_advisory_lock` (could stall migrations) and connect to the server's `postgres` maintenance database; the local owner is a superuser and can bypass the trigger (`session_replication_role`). | Each needs cluster-level setup that belongs with deployment (M11). | Fixing now in Docker only. |

## M2. Pricing rules and AI quote builder (2026-10-26)

**In plain words.** A customer's message becomes a draft quote, but the model only *reads*: it
returns parts, quantities, catalog material codes, post-processing requests, a named due-date rule
and flags. It has no field for a price, discount or date. Code turns the rule into a date, works
out what is still missing, and prices the quote from dated, insert-only price versions. Staff add
the grams and minutes per part (no file measurement until M7), correct anything, and approve; only
staff can approve, only when nothing is missing, and approval creates the order in the same
transaction. Every model call goes through one gateway that validates the reply with our own
schema, repairs once, and records tokens, cost and outcome. A 45-message eval measures accuracy,
how often the model guesses instead of flagging, and whether injected instructions are resisted.

| # | Decision | Why | Alternative considered |
|---|---|---|---|
| D35 | Price rules are **dated, insert-only versions** (migration 0005). Triggers block UPDATE/DELETE/TRUNCATE for every role, and rates can only be added in the transaction that created their version (`created_txid`). A version must price every material, process and post-processing kind; it cannot be backdated. | Any quote can be explained by the version it names; changing prices never rewrites history. | One editable table (simpler, but old quotes become unexplainable). |
| D36 | **The AI gateway lives in the engine** (Python, pydantic), not the web (zod). zod still validates the web forms. | The engine owns the database, prices and permissions; M6 and M8 will reuse the gateway. **Deviation from MILESTONES ("Quote schema (zod)").** | Gateway in the web. |
| D37 | Structured outputs (`output_config.format` with `anthropic.transform_schema`), then **our own pydantic validation** with context (the live catalog), one repair turn showing the errors, then reject. | The API's guarantee is not our guarantee (hard rule 2). Forced tool use is rejected on current models. | Tool use for JSON; trusting the API's schema check. |
| D38 | The model returns a **due-date rule**, never a date; for `on_date` the year only if the customer wrote one. `resolve_due()` computes the date in the shop's time zone. | The brief's rule: AI picks a named rule, code computes. A model guessing the year is still a model computing a date. | Model returns an ISO date. |
| D39 | **Grams and minutes per part are staff-entered** in M2; the price is "pending" until they are. | Prices depend on them, and the model must not guess numbers that drive a price (hard rule 1). M7's file checker will fill them. | Model estimates from the description. |
| D40 | `AI_MODE=live\|fake\|off`. Tests, the gate, CI and browser tests use `fake` (prepared replies), so they are offline, deterministic and free. With `off`, no key, or any model failure, the quote is still created empty for manual entry. | The app must work without the model; the gate must never spend money. | Mocking the SDK. |
| D41 | The model call runs **outside** the database transaction; a retry with a used idempotency key skips the call. Two simultaneous first attempts may both call the model, but only one quote is written. | No lock is held for seconds; retries cost nothing. The rare double call is cheaper than holding a row lock across a network call. | Claim the key first and hold it during the call. |
| D42 | `ai_calls` and `quote_requests` are append-only; a decided quote and its lines are frozen by trigger; the app role cannot update `ai_draft`, `request_id` or `customer_id` (column grants). | The AI's original reading and the customer's words stay as evidence of what each side said. | Code-only rules. |
| D43 | Every call records cost in **micro-USD** from dated prices in `config/models.toml`; the instructions are marked cacheable and the eval reports how many requests read the cache. | Costs are traceable to a price and a date (hard rule 8). | Logging tokens only. |
| D44 | Model: **Claude Opus 5.5 at low effort** is the configured default; the eval is built to compare it with Claude Haiku 5.5 on the dev split so the choice is made on measured accuracy and cost. Server-side refusal fallbacks are not enabled: a refusal becomes an empty draft that staff fill in, which a human does anyway. | Model choice trades cost against accuracy, so it is the owner's call, from numbers. | Picking the cheaper model up front. |
| D45 | Eval replies are saved per model and prompt version and committed, so `RESULTS.md` can be regenerated without spending; the runner stops at a cost cap and exits with a message (never invented numbers) when it has no model access. | Reproducible numbers (hard rule 11). | Calling the model on every run. |
| D46 | `QuoteDetail` hides the shop's working (grams, minutes, AI cost, requests for staff) from customers, and shows them the price only once approved. Planners see the staff view read-only. | Customers should not see internal numbers or unapproved prices. | Separate customer and staff endpoints. |
| D47 | **Provider: DeepSeek** (the owner's account). The gateway gains a `DeepSeekClient` for the OpenAI-format chat API in JSON-output mode, with plain `httpx2` calls (no new SDK). Each model in `config/models.toml` names its provider; `quote_extract` uses `deepseek-flash` at low reasoning effort, compared against `deepseek-v4-pro`. Claude stays supported by config. Costs are logged at DeepSeek's **peak** price so they are never understated. **Supersedes D44's model choice.** | DeepSeek's JSON mode guarantees JSON, not our schema, so the schema goes in the system prompt and our pydantic validation stays the guard (hard rule 2). | DeepSeek's Anthropic-format endpoint (less code, but no documented support for the structured-output field we send); the `openai` SDK (another dependency for one POST). |
