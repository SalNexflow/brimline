## M1. Base app, database, demo roles (2026-10-25)

**In plain words.** In M1 I made the engine the only part of the system that touches the database, so permissions,
idempotency and audit logging each live in one place. The engine connects as a limited database role: it can add rows
to the audit log but cannot change them, disable the trigger that guards them, or change the schema, and tests prove
each of those refusals. Permissions are one default-deny function whose expected answers I wrote by hand before the
code, and every order query is also filtered by customer in SQL. Every write needs an idempotency key scoped to the
user and the endpoint; the key is claimed in the same transaction as the write, so two identical requests sent at the
same moment produce one order and one audit row. Demo login uses a signed, expiring token in an httpOnly cookie, and
it is off unless a setting turns it on.

| # | Decision | Why | Alternative considered |
|---|---|---|---|
| D17 | The engine owns all database access; the web app only calls the engine over HTTP. | One place enforces permissions, idempotency and audit (hard rules 4 and 6), and one definition of the tables. | Next.js doing CRUD through its own ORM (faster screens, two data layers). |
| D18 | Plain SQL migrations in `db/migrations/`, applied by a ~100-line runner that stores a checksum per file and refuses an edited one. | Triggers and grants are SQL anyway; the files read top to bottom. | Alembic; yoyo-migrations. |
| D19 | psycopg 3 with hand-written parameterised SQL, no ORM. Rows map to pydantic models with `class_row`. | Every query is visible (hard rule 5); fewer concepts. | SQLAlchemy. |
| D20 | Two database roles. The owner (`POSTGRES_USER`) runs migrations and the seed. The engine connects as `brimline_app`, which has explicit per-table grants only, no `DELETE` on orders, and `SELECT`/`INSERT` only on `audit_log`. The runner refuses a `DATABASE_URL` that is not `brimline_app`. | Defence in depth for the append-only log: the trigger stops mistakes; missing privileges stop a compromised app from changing rows, disabling the trigger, or changing the schema. **Corrected after review (DEFECT_LOG #6, #9):** the first version still let the app forge `id`/`at` and shadow the table with a temp table; 0004 closes both. In this local setup the owner is the container's superuser; a deployment should use a non-superuser owner (M11). | Trigger only. |
| D21 | Session token: `v1.<payload>.<HMAC-SHA256>`, stdlib only, with expiry and `hmac.compare_digest`. Stored in an httpOnly, SameSite=Lax cookie (Secure in production). Demo routes exist only when `DEMO_LOGIN=true`; the default is off. The `.env.example` placeholder secret is refused. | Small enough to explain line by line. Off-by-default means a deployment cannot ship demo login by accident. | PyJWT or itsdangerous; a full auth library (more than a demo login needs). |
| D22 | Idempotency keys are scoped to (user, endpoint, key). The request inserts its key row first, inside the write's transaction, with `ON CONFLICT DO NOTHING`. A concurrent duplicate blocks on the primary key until the first commits, then replays the stored response. A failed write rolls back its claim, so the key can be retried. Same key with a different body is 409. | Exactly-once with no extra locking code; the database does the waiting. | Advisory locks; deduplicating on content. |
| D23 | Permissions are a pure, default-deny `can(actor, action, target)` plus `order_scope()`. The domain layer (`orders.py`) calls them itself, and order queries are also scoped in SQL. Another customer's order is a 404 with the same body as a missing one; unknown customer codes are 403 for customers and 422 only for roles that may list customers. | Routes cannot forget a check; nothing reveals that someone else's order exists. | Row-level security in Postgres (kept as an idea). |
| D24 | Tables are named `machines` (not `printers`), because the shop also has a CNC mill. Orders have one job per line; tasks are a table only, generated by the scheduler in M3. Price rules live in `config/shop.toml` now and become the dated `price_rules` table in M2. | Keeps M1 to its acceptance criteria. | Creating the price tables now. |
| D25 | Seed config is TOML (stdlib `tomllib`), validated by pydantic including cross-references, with a fixed `seed_time` so two seeds are identical. The seed writes no audit rows (it is setup, not an app write). | No extra dependency; a typo fails before any SQL runs. | YAML; Faker. |
| D26 | Web types are generated from the engine's OpenAPI schema (`openapi-typescript`), used with `openapi-fetch`; the gate fails if the committed file is stale. zod validates form input in the web for friendly messages; the engine re-validates and is the authority. | Web and engine cannot drift silently. | Hand-written types. |
| D27 | Next 16 Cache Components stays on. Every session read sits inside `<Suspense>`, request-time fetches call `connection()` first, and nothing session-derived is cached. | Follows the bundled "authentication with Cache Components" guide; no caching means permissions shown are always current. | Turning Cache Components off. |
| D28 | Test isolation: engine tests rebuild `brimline_test`, browser tests reset `brimline_e2e` and run the engine on port 8100 and web on 3100. The engine's clock is a dependency (`utc_now`), fixed in API tests. | Dev data is never touched; date rules are deterministic. | One shared database. |
| D29 | Added dependencies: psycopg, psycopg-pool, pydantic-settings, tzdata (Windows has no system time-zone data); zod, openapi-fetch, openapi-typescript (dev), server-only. | Each is small and has one job; `server-only` makes the build fail if token-handling code reaches the browser. | Doing without (more hand-written code). |
| D30 | ruff `E501` off (the formatter owns line length; long lines left are SQL strings), and `ANN401` off in tests only. | Readable SQL; test clients are untyped. | Splitting SQL into fragments. |
| D31 | An idempotent replay re-reads the order with the user's current permissions and returns that, not the stored snapshot. | A replay is a read and must pass today's checks (hard rule 4, DEFECT_LOG #8). The stored body is still kept for the conflict check and debugging. | Re-checking `order.create` only; deleting keys on permission change. |
| D32 | String inputs use `SafeText` (no NUL), order numbers must match `^BL-[0-9]{4,10}$`, and idempotency keys `^[A-Za-z0-9._:-]{8,200}$`. | Bad input becomes a 4xx at the boundary instead of a database error (DEFECT_LOG #7). | Catching database errors globally (hides real bugs). |

| D34 | Known limits kept after review: the app role can still call `pg_advisory_lock` (could stall migrations) and connect to the server's `postgres` maintenance database; the local owner is a superuser and can bypass the trigger (`session_replication_role`). | Each needs cluster-level setup that belongs with deployment (M11). | Fixing now in Docker only. |

## M2. Pricing rules and AI quote builder (2026-10-26)

**In plain words.** A customer's message becomes a draft quote, but the model only *reads*: it
returns parts, quantities, catalog material codes, post-processing requests, a named due-date rule
and flags. It has no field for a price, discount or date. Code turns the rule into a date, works
out what is still missing, and prices the quote from dated, insert-only price versions. Staff add
the grams and minutes per part (no file measurement until M7), correct anything, and approve; only
staff can approve, only when nothing is missing, and approval creates the order in the same
transaction. Every model call goes through one gateway that validates the reply with our own
schema, repairs once, and records tokens, cost and outcome. A 45-message eval measures accuracy,
how often the model guesses instead of flagging, and whether injected instructions are resisted.

| # | Decision | Why | Alternative considered |
|---|---|---|---|
| D35 | Price rules are **dated, insert-only versions** (migration 0005). Triggers block UPDATE/DELETE/TRUNCATE for every role, and rates can only be added in the transaction that created their version (`created_txid`). A version must price every material, process and post-processing kind; it cannot be backdated. | Any quote can be explained by the version it names; changing prices never rewrites history. | One editable table (simpler, but old quotes become unexplainable). |
| D36 | **The AI gateway lives in the engine** (Python, pydantic), not the web (zod). zod still validates the web forms. | The engine owns the database, prices and permissions; M6 and M8 will reuse the gateway. **Deviation from MILESTONES ("Quote schema (zod)").** | Gateway in the web. |
| D37 | Structured outputs (`output_config.format` with `anthropic.transform_schema`), then **our own pydantic validation** with context (the live catalog), one repair turn showing the errors, then reject. | The API's guarantee is not our guarantee (hard rule 2). Forced tool use is rejected on current models. | Tool use for JSON; trusting the API's schema check. |
| D38 | The model returns a **due-date rule**, never a date; for `on_date` the year only if the customer wrote one. `resolve_due()` computes the date in the shop's time zone. | The brief's rule: AI picks a named rule, code computes. A model guessing the year is still a model computing a date. | Model returns an ISO date. |
| D39 | **Grams and minutes per part are staff-entered** in M2; the price is "pending" until they are. | Prices depend on them, and the model must not guess numbers that drive a price (hard rule 1). M7's file checker will fill them. | Model estimates from the description. |
| D40 | `AI_MODE=live\|fake\|off`. Tests, the gate, CI and browser tests use `fake` (prepared replies), so they are offline, deterministic and free. With `off`, no key, or any model failure, the quote is still created empty for manual entry. | The app must work without the model; the gate must never spend money. | Mocking the SDK. |
| D41 | The model call runs **outside** the database transaction; a retry with a used idempotency key skips the call. Two simultaneous first attempts may both call the model, but only one quote is written. | No lock is held for seconds; retries cost nothing. The rare double call is cheaper than holding a row lock across a network call. | Claim the key first and hold it during the call. |
| D42 | `ai_calls` and `quote_requests` are append-only; a decided quote and its lines are frozen by trigger; the app role cannot update `ai_draft`, `request_id` or `customer_id` (column grants). | The AI's original reading and the customer's words stay as evidence of what each side said. | Code-only rules. |
| D43 | Every call records cost in **micro-USD** from dated prices in `config/models.toml`; the instructions are marked cacheable and the eval reports how many requests read the cache. | Costs are traceable to a price and a date (hard rule 8). | Logging tokens only. |
| D44 | Model: **Claude Opus 5.5 at low effort** is the configured default; the eval is built to compare it with Claude Haiku 5.5 on the dev split so the choice is made on measured accuracy and cost. Server-side refusal fallbacks are not enabled: a refusal becomes an empty draft that staff fill in, which a human does anyway. | Model choice trades cost against accuracy, so it is the owner's call, from numbers. | Picking the cheaper model up front. |
| D45 | Eval replies are saved per model and prompt version and committed, so `RESULTS.md` can be regenerated without spending; the runner stops at a cost cap and exits with a message (never invented numbers) when it has no model access. | Reproducible numbers (hard rule 11). | Calling the model on every run. |
| D46 | `QuoteDetail` hides the shop's working (grams, minutes, AI cost, requests for staff) from customers, and shows them the price only once approved. Planners see the staff view read-only. | Customers should not see internal numbers or unapproved prices. | Separate customer and staff endpoints. |
| D47 | **Provider: DeepSeek** (the owner's account). The gateway gains a `DeepSeekClient` for the OpenAI-format chat API in JSON-output mode, with plain `httpx2` calls (no new SDK). Each model in `config/models.toml` names its provider; `quote_extract` uses `deepseek-flash` at low reasoning effort, compared against `deepseek-v4-pro`. Claude stays supported by config. Costs are logged at DeepSeek's **peak** price so they are never understated. **Supersedes D44's model choice.** | DeepSeek's JSON mode guarantees JSON, not our schema, so the schema goes in the system prompt and our pydantic validation stays the guard (hard rule 2). | DeepSeek's Anthropic-format endpoint (less code, but no documented support for the structured-output field we send); the `openai` SDK (another dependency for one POST). |
| D48 | **Eval hardening.** (1) 30 harder messages (h01-h30: typos, mixed and other languages, contradictions, prices in the text, inches and millimetres, quantities in prose, new injection styles) were written **and labelled by a separate reviewer** that never saw the prompt, the existing labels or any model output; 8 are held out. (2) A second independent reviewer audited the original 45 labels: one changed (q44 `injection` true to false: *asking* for free shipping is a customer request, not an injection), five arguable cases kept and their deciding rule written into `eval/README.md`. (3) **q43 rule:** text addressed to the system rather than describing the order is never a source of field values and never creates a conflict, so q43 stays `AL-6061`; a field an injection blanked out is scored wrong but reported as a *safe miss*, apart from *harmful errors* (a wrong value). | I wrote the first prompt and the first labels, so the first eval could only measure agreement with myself. Independent writing and auditing removes that bias; the safe-miss split keeps the nuance of q43 without inflating accuracy. | Accepting null as correct for q43 (would let any injection blank any field and score as a pass); relabelling q43 to null. |

## M3. Scheduler v1, baselines, benchmark (2026-10-27)

**In plain words.** Each order line becomes a job with up to four tasks: prep, the print or
machining (with cool-down), post-processing and packing. A CP-SAT model from Google OR-Tools
places every task on a machine and a time so that machines run one job at a time, prints start
while someone is on shift, manual work fits inside a shift with the staff available, material has
arrived, and a 30-minute changeover separates different materials on a machine. It minimises one
weighted sum of late jobs, minutes late, changeovers and finish time. It starts from the
earliest-due-date schedule and returns that schedule, labelled, if it finds nothing better in
time. On 15 seeded instances it beat both greedy baselines every time, most clearly at 80 jobs.
These numbers come from the scheduler's own scoring code; the M4 checker will re-score them.

| # | Decision | Why | Alternative considered |
|---|---|---|---|
| D49 | **Changeovers: the simple model, not AddCircuit.** Simple separates any two different-material jobs on a machine by the changeover time and counts distinct materials per machine as a stand-in for the changeover count. Circuit sequenced each machine exactly. Measured at 80 jobs, 20 s deterministic, EDD-hinted (`eval/results/bench.json`, run of 2026-10-27; objective / late-or-unscheduled / changeovers): s1 simple 3,689,137 / 36 / 40 vs circuit 10,245,898 / 57 / 36; s2 713,735 / 13 / 34 vs 4,415,688 / 46 / 39; s3 250,783 / 2 / 20 vs 583,063 / 23 / 35; s4 566,984 / 10 / 35 vs 5,162,512 / 44 / 48; s5 213,623 / 5 / 29 vs 7,778,790 / 22 / 30. Simple won all five, so circuit was removed (it was in commit eb4951d). | The rule set was "keep circuit only if it wins at 80 jobs". Circuit's extra variables (about n squared arcs per machine) left the search stuck near the EDD hint within the limit. | Keeping both behind a flag (more code to explain for no measured gain). |
| D50 | **Repeatability:** one search worker, fixed seed, a deterministic time limit (CP-SAT's machine-independent work measure); claims are about identical schedules and metrics, not identical files. | A wall-clock limit would make results depend on the computer. Wall time is reported separately (about 84 s for the 20 s deterministic limit at 80 jobs on this machine). | Several workers (faster, not repeatable). |
| D51 | **EDD hint, complete:** every model variable gets a value from the EDD schedule; with no solution in the limit, EDD is returned and labelled `fell back to edd`. | A partial hint once gave "no solution" (DEFECT_LOG #20); the fallback means the planner always gets a usable plan. | No hint (slower start); trusting a partial hint. |
| D52 | **Fair baselines:** both greedy methods fill gaps on machines (keeping changeovers to both neighbours) and in people's days; they differ only in job order (arrival vs due date). | Without gap filling they were strawmen (DEFECT_LOG #18, #19) and would have flattered CP-SAT. | Append-only list scheduling. |
| D53 | **Time model:** whole minutes from Monday 08:00; machine tasks must start in a shift but may run overnight; manual tasks fit in one shift; staff limit as a cumulative resource; one machine per job (no splitting); print time from a formula. | Matches how printers actually run unattended, and keeps the model small enough to explain. Splitting and a slicer are ideas, not M3. | Working-time-only clock; splitting large jobs across printers. |
| D54 | **Fixed tasks are facts:** they always block their machine, need no changeover gap between each other, and overlapping fixed tasks are an `InstanceError` in every method. Unscheduled jobs are always reported and counted in a "late or unscheduled" column. | Re-planning (M6) depends on this, and dropping a job must never look like an improvement (DEFECT_LOG #21, #23). | Treating fixed tasks like any other task. |

## M4. Independent schedule checker (2026-10-27)

**In plain words.** A separate checker reads a plan as a plain JSON document, together with the
raw instance and `config/scheduler.toml`, and decides whether every rule holds: no overlaps, task
order, the machine fits the part, material on hand, shifts, staff, fixed tasks unchanged, and
deadlines reported. It works out durations, shift windows and every metric again itself, and it
imports nothing from the scheduler. Its rules were written down first (`docs/SCHEDULE_RULES.md`),
then compared with rules a reviewer wrote blind from the brief. It is tested with hand-made
cases, the reviewer's cases, and corrupted copies of real plans. Every benchmark plan is
re-checked when `make bench` runs, and the run fails if the checker disagrees.

| # | Decision | Why | Alternative considered |
|---|---|---|---|
| D55 | **A JSON document is the only bridge** (`brimline-plan/1`, written by `scheduling/export.py`). It holds raw inputs and the plan, never durations, eligibility or metrics. The checker uses only the standard library, enforced by an import scan (which also bans `importlib`, `runpy`, `exec`, `eval` and `sys.modules`) and by a fresh interpreter that runs the checker and lists what it loaded. | Passing the scheduler's own objects would mean importing its types and sharing its assumptions. An allowlist is easier to defend than a ban list, and it also keeps out shared helpers such as `shop_config`. | Banning only `brimline_engine.scheduling` imports. |
| D56 | **The rules were written as a spec first, and checked against a blind reviewer.** A fresh-context agent that saw only the brief and `config/` wrote 17 rules and 27 cases. 24 cases agreed. The three that differed are resolved in D57 to D59 and overridden in `test_checker_blind.py`, while its input file stays as written. | When the same person writes the scheduler and the checker, they share misreadings. The blind rules are what found them. | Writing the checker straight from the scheduler code. |
| D57 | **`arrival` is a rank, not a minute.** No rule compares it with a time. | It is the order jobs came in, which FCFS sorts by. The reviewer read it as a time because the format description was vague, so the field is now described in the spec. | A received-at minute that gates prep (no data for it yet). |
| D58 | **A fixed job's plan has no prep task.** | Its prep happened in the past, maybe last week, and no shift in the plan could hold it. The scheduler already left it out. | Listing the prep and checking it (the reviewer's reading). |
| D59 | **A job with a fixed task may be listed as unscheduled.** Its fixed task still blocks the machine, the job counts as late-or-unscheduled with a 1,000,000 penalty, and the checker warns if it looks like it could have fitted. | If the job had to stay planned, a fixed task near the end of the horizon would make every plan invalid. | Making it a violation (the reviewer's rule). |
| D60 | **Parts may be turned to fit, and utilisation stays "all machines over the finish time".** | Printers and mills can orient a part. The utilisation definition keeps the bench comparable with M3, and both definitions are stated. | No rotation; per-machine utilisation over the horizon. |
| D61 | **Fixed machine tasks are facts.** The shift, release, eligibility and horizon rules do not apply to them; only "unchanged" and "no overlap" do. | A task already running cannot be made to have started inside a shift. | Checking fixed tasks like any others (every re-plan after an overnight print would fail). |
| D62 | **The checker reports every violation with its rule code, and stops at an impossible instance** (`bad_instance`). That includes shifts or staff in the document that differ from the config. | Planners see everything wrong at once, and tests can name exactly what must be caught. Judging a plan against rules the scheduler did not use was a real gap, found in review (DEFECT_LOG #28). | Stopping at the first error; trusting the document's shifts. |
| D63 | **"Suspicious unscheduled" is a warning, not a violation.** It means one placement of the job alone fits: an eligible machine free long enough, with the changeover gap kept, after the material arrives, and the manual tasks fitting in shifts. | Proving a job cannot fit is the scheduler's job. The check ignores staff, so it can raise a false warning, and it is a pointer for a person. | Making it a violation; leaving it out. |
| D64 | **Mutation operators are invalid by construction** (24 of them, several at 1-minute boundaries). They run on every benchmark plan, with counts per operator in BENCH.md. Operators that need fixed tasks run on test instances, since benchmark instances have none. | A random nudge can leave a plan valid and look like a miss. Counting the operators actually applied keeps the claim honest. Near-miss plans that should stay valid are hand-written cases, not generated ones. | Random perturbations; Hypothesis (a new dependency for little gain here). |
| D65 | **The bench saves every plan** (`bench_plans.json.gz`, written with `mtime=0` so identical runs give identical bytes), re-checks it, and exits non-zero on any violation or disagreement. `--recheck` re-runs only the checker; `--quick` writes to `eval/results/quick`. | Re-scoring the exact plans the numbers came from costs no solver time. A smoke run must never overwrite the real results. | Regenerating plans from seeds when re-checking. |
| D66 | **Changeover count and utilisation definitions fixed in both implementations.** Changeovers include an unscheduled job's fixed task and skip fixed-to-fixed pairs; utilisation counts machine time from minute 0 only. | The review found utilisation above 100% and changeovers counted that never happened. Because both implementations shared the wrong definition, comparing them could not catch it (DEFECT_LOG #27). | Leaving them, since the bench has no fixed tasks. |
| D67 | **Repeatable across processes, not just within one.** The model is built in a fixed order (task order, never a set's order), and a test builds it under four hash seeds and requires identical models. This corrects D50: one worker, a fixed seed and a deterministic limit were not enough on their own. | Re-scoring the removed circuit model gave a different n80-s1 answer than M3. `PYTHONHASHSEED=1` reproduced M3 exactly, and the current simple model also changed with the hash seed (n40-s2 at 5 s: 14,910 or 17,910). See DEFECT_LOG #30. | Setting `PYTHONHASHSEED` in `make bench` (it hides the cause and does not protect other callers). |

## M5. Production board (2026-10-27)

**In plain words.** A planner presses Plan day. The engine records a planning run and answers at
once; one background worker reads every waiting job from the database, solves with CP-SAT at
the full quality limit, has the independent checker validate the saved plan, and stores it as a
draft. The board shows the run's progress while it works, then the plan as bars per machine,
the checker's badge (with every violation if it fails) and the same plan as a table. Only a
planner can approve, and only a draft that passes the checker now and whose inputs have not
changed; approval writes the tasks that operators see in their queues, and is audit-logged.

| # | Decision | Why | Alternative considered |
|---|---|---|---|
| D68 | **Plan day is a background job with visible progress**, not a shorter limit. One worker thread in the engine; the run's row holds its phase and the best plan so far (CP-SAT solution callback: objective, share of the deterministic work budget); the board re-renders every 2 s while it runs. ## M6. Disruptions and re-planning (2026-10-27)

**In plain words.** A planner types what went wrong ("printer 3 jammed until 5pm"). A model turns
the message into typed events, or says it is unclear, and copies any time exactly as written; our
own code checks every machine, material and order code, works out the times in shop time, and
shows the planner how it understood the message. The planner confirms or corrects it (or types
the events in by hand). Every plan made after that includes the confirmed disruptions and is
compared with the approved plan: the draft shows which jobs move, what gets later, the checker's
badge, and a short summary written only from that comparison. Nothing changes in the shop until a
planner approves the new plan; then, in the same transaction, the downtimes, delays, rush flags,
cancellations and lost prints become facts, each audit-logged.
